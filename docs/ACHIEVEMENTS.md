## Unlock notifications (6.6)

Append-only migration `008_achievement_notifications.sql` advances SQLite to **schema v8**. `achievement_notification_receipts` references permanent unlock IDs, with a unique receipt per ID. Existing unlocks receive `baseline` rows with NULL `claimed_at`; upgrading does not replay historical achievements or invent delivery timestamps. New unlocks have no receipt until claimed. Unlock records, their initial timestamps and all writing/activity remain unchanged; migrations 001–007 are unchanged.

`claim_achievement_notifications` takes no client arguments and runs off the UI thread under the existing database mutex. In one IMMEDIATE transaction it validates permanent unlocks and existing receipts, inserts `claimed` receipts using the native UTC clock, and returns only newly claimed committed rows after commit. Insert/commit failures roll back claims and leave them retryable. Claim failures never change an already committed chapter save into a failure. Concurrent callers and reopening the database cannot claim an ID twice. Malformed stored receipts fail without automatic repair.

This is **at-most-once claiming, not guaranteed human delivery**. A crash, unmount or lost response after the claim commits can miss the transient notice; the permanent achievement remains visible on Achievements. No acknowledgement protocol or automatic replay is claimed. Baseline timestamps remain absent; claimed timestamps record retrieval, not proof of display.

Successful committed chapter saves/retries and book deletions emit the best-effort native `achievement-unlocks-changed` wakeup; explicit reconciliation emits it when new unlocks were committed. Event payloads are not evidence: the global collector always reads the native claim command. It subscribes before the initial drain, coalesces overlapping wakeups, retries on focus/visible resume and cleans up listeners. Hidden documents do not start claims; an already dispatched transaction can finish. Startup reconciliation is covered by the initial drain. Failed listener registration retains startup/focus/visible fallback. Browser previews have no fake notification persistence.

The collector batches newly claimed names in catalog order and queues later batches. A polite live region announces the notice without moving typing focus. The cream/sage Trophy card appears at the lower right, or inside the topmost shared Modal's notification slot so Radix's dialog focus/ARIA boundaries remain intact. The generic slot/provider has no achievement dependency. Notices survive navigation and dismiss after eight seconds, paused during hover, keyboard focus or hidden state; resuming starts a fresh eight-second interval. Explicit dismissal restores the previous connected control only when the notice owned focus. No global Escape override, sound, OS notification permission or decorative animation is added. English copy stays in `en.ts`.

## Production page (6.5)

`AchievementsPage.tsx` replaces the existing section's placeholder and displays all eight catalog cards, a saved-unlock count, Refresh/Retry and explicit loading/error/confirmed-empty feedback. It uses `getAchievementUnlocks()` first so previously earned rows can remain visible even if subsequent reconciliation fails. `refreshAchievements()` then reconciles on the native date and returns its post-commit snapshot. UI counters/dates come from validated committed rows. The page does not infer unlocks from evaluation or produce per-achievement notifications.

An outer page cache survives section navigation; the active reader mounts only while visible. Activation, local-date changes, window focus, visible resume and manual retry invalidate the request. Each effect has a cancellation guard: late reads cannot start hidden reconciliation, and superseded read/refresh results cannot overwrite newer state. An already dispatched native transaction is not cancelled; it may commit safely under the existing idempotent contract. A later page activation reads its committed result.

Initial loading/failure stays unknown rather than a fake empty collection. Confirmed empty feedback appears only after successful native reconciliation. Failed later requests retain the last confirmed cards/counts and explicitly label that retained view. Later snapshots cannot remove a previously confirmed permanent ID or rewrite its policy version/initial timestamp; such contradictions are reported without discarding the cache. Browser preview has no native persistence fallback and explains the desktop requirement. Native errors are mapped to centralized copy, not exposed as raw database messages or paths.

The native unlock API currently returns saved unlocks rather than lifetime counter evidence. Consequently locked cards show Progress unavailable; the page does not infer numeric progress from current manuscript lengths or independently queried partial calendar ranges. Cards still accept valid optional checks for future authoritative progress support. Saved UTC instants are unchanged; display dates resolve the current browser timezone when cards render, including after timezone travel and focus refresh.

## Card presentation (6.4)

`AchievementCard` accepts a stable `achievementId`, a validated saved `unlocks` collection (null when unavailable), and an optional committed-evidence `check`. It renders the catalog name/requirement, decorative Lucide illustration and textual saved status. The pure `getAchievementCardState` helper validates row IDs/timestamps and progress shape. Persisted rows win over changed/unknown checks; only persisted evidence supplies Unlocked and its original date. A known empty saved list means not yet unlocked, not necessarily below the eligibility threshold. Eligible checks remain Locked with an explicit confirmation hint.

Missing/failed saved-status reads show Status unavailable without invented zero counts or dates. When checks are available, known progress has full formatted counts and accessible bounds; positive incomplete lower bounds say At least, and uncertain zero/malformed/mismatched evidence has no numeric bar. Already unlocked cards show their saved date without claiming current counters. The End's missing mark-complete action is explained with text only.

Cards are named read-only articles, with H3 titles, associated requirements, decorative nonfocusable icons and visible status labels. They have no fake unlock action or live notification. All English copy remains centralized. The separate fixture provides presentation samples for testing only; production native IO, caching/loading, last-success retention and page composition belong to 6.5. The parent should retain its last validated saved unlock collection during refresh rather than replacing known unlocks with an empty collection on failure. No persistence/evaluation rules changed in 6.4. See [design and verification](DESIGN_SYSTEM.md#achievement-cards-64).

## Catalog

All thresholds are inclusive (`confirmed value >= threshold`). Scope is global to the local library, across all books and chapters; changing a selected book or calendar filter must not change achievement eligibility. IDs are permanent machine identities, independent of translation, display order and policy version.

| Stable ID          | Name             | Metric                       | Threshold | Exact criterion                                                                          |
| ------------------ | ---------------- | ---------------------------- | --------- | ---------------------------------------------------------------------------------------- |
| `first_words`      | First Words      | `credited_words`             | 100       | At least 100 committed credited words.                                                   |
| `getting_started`  | Getting Started  | `credited_words`             | 1,000     | At least 1,000 committed credited words.                                                 |
| `storyteller`      | Storyteller      | `credited_words`             | 10,000    | At least 10,000 committed credited words.                                                |
| `novelist`         | Novelist         | `credited_words`             | 50,000    | At least 50,000 committed credited words.                                                |
| `consistency`      | Consistency      | `completed_scheduled_days`   | 7         | On 7 distinct stored local dates, at least one scheduled book daily goal was reached.    |
| `dedicated_writer` | Dedicated Writer | `completed_scheduled_days`   | 30        | On 30 distinct stored local dates, at least one scheduled book daily goal was reached.   |
| `goal_keeper`      | Goal Keeper      | `completed_daily_goals`      | 10        | 10 distinct `(sourceBookId, localDate)` pairs have a reached scheduled daily goal.       |
| `the_end`          | The End          | `explicitly_completed_books` | 1         | At least one book has persisted, validated explicit completion evidence (`completedAt`). |

The product says “complete 7/30 scheduled writing days,” not “maintain a 7/30-day streak.” These are **cumulative completed days**, not current or longest streaks. Missed days do not reset these totals. Multiple reached book goals on one date count as one completed day but multiple daily goals. For example, two books meeting their goals on five dates contribute five completed days and ten daily goals. No book must reach both thresholds by itself.

## Authoritative evidence

- **Words:** sum committed editor-origin `creditedWords` using [activity policy 1](ACTIVITY_MODEL.md). Positive net additions, including paste, earn credit; deletions do not subtract past credit. Same-length replacement, formatting and zero-delta saves add zero. Import/restore operations earn zero new credit. Existing manuscript length, book targets and unsaved editor counts are not substitutes for activity records. Deleting/retyping can earn later credit under the existing policy; achievements do not change it.
- **Scheduled days and daily goals:** use the historical daily statistics definition from tasks 5.3/5.7. A qualifying result has `scheduled === true`, a positive applicable daily goal and `state === 'reached'` from committed credited activity. Sealed day plans and effective schedule/goal history remain authoritative; current settings never reinterpret prior dates. A rest day, positive writing without a configured goal, or an unmet goal does not qualify. Today qualifies immediately once its goal is reached; there is no extra end-of-day wait or invented grace credit.
- **Uniqueness:** word evidence is keyed by `(operationId, segmentIndex)`; daily goal evidence by `(sourceBookId, localDate)`; completed days by `localDate`. Do not sum overlapping query pages, retries or repeated snapshots twice. Multiple chapters of one book share its one daily goal. Retained activity from deleted books/chapters still counts, using immutable source IDs rather than nullable live foreign keys.
- **Time:** inspect stored local calendar dates through the current local `today`, inclusive, consistent with existing statistics/streak readers. Exclude future-labelled activity until that date; never shift old dates into the device's new timezone. Repeated appearances of the same date during timezone travel count once for a given key. Use civil calendar dates, not UTC slicing or elapsed 24-hour intervals. Clock rollback does not erase an existing unlock.
- **History and uncertainty:** evaluation must inspect all recorded history under a consistent snapshot, paging beyond the statistics API's 366-day window when necessary. A displayed calendar month, a per-book request or a streak summary is insufficient evidence for these cumulative totals. Missing legacy history and read/validation failures stay unknown. Confirmed lower bounds may establish a reached threshold; insufficient or unavailable evidence must never invent an unlock or claim a known exact total. Do not backfill credit from old manuscript counts.
- **Numeric safety:** persisted counts must be validated nonnegative integers. Aggregate with checked arithmetic or threshold-saturating comparisons; never allow overflow, floating-point rounding, `NaN` or an unsafe JavaScript sum to open a badge. Exact lifetime totals are unnecessary to prove these small thresholds.

## Explicit book completion dependency

`Book.completedAt` / `books.completed_at` already exists and is preserved by metadata edits. A non-null validated native snapshot is explicit completion evidence. A known empty collection contributes zero; a failed book read is unknown. Missing word targets, empty chapters or a reached/exceeded word target never imply completion. Several explicit completions still unlock only one `the_end` achievement.

**Current gap:** there is no public mark-complete command or UI. Task 6.1 neither sets this field nor infers completion. Follow-up **ACH.1** must provide an explicit revision-checked, commit-based completion action. Coordinate its completion write and durable unlock in task 6.3 so a subsequent book deletion cannot lose a newly earned achievement. Until that action exists, a library without persisted explicit completion evidence cannot earn The End. A book deleted before durable completion evidence/unlock was recorded cannot be reconstructed from its retained writing activity; no retroactive completion is fabricated.

## Unlock lifecycle contract for 6.2/6.3

1. The pure evaluator reports eligible stable IDs from validated committed evidence. One save may qualify for several thresholds; evaluate every rule independently. UI drafts, optimistic metadata and failed transactions cannot qualify.
2. Persistence owns one unlock per stable achievement ID for the local library. Policy version is audit metadata, not part of a uniqueness key that would unlock the same badge twice. Retries, app restart and concurrent evaluation must be idempotent.
3. Once durably unlocked, retain the achievement despite later deletions, changed targets/schedules, undo, book reopening or clock rollback. Never cascade-delete unlocks with books. Optional book evidence may retain a source ID or detach its live reference; no manuscript text is needed.
4. `unlockedAt` will be the native UTC instant of the first successful unlock insertion, not an instant guessed from a local date or aggregate threshold. Historical eligible activity may be recognized on first evaluation after upgrade; do not pretend that discovery happened at an unobserved earlier time. Notifications and “unlocked” UI follow successful persistence, never merely an evaluator result.
5. A later policy change needs explicit version/migration review and must preserve prior IDs/unlocks. No SQL migration, evaluation service or save-path integration is implemented in 6.1. Imported/restored text must not manufacture new credit; preserving actual historical records/unlocks belongs to the separately approved backup/restore work.

## Evaluation boundary (6.2)

`evaluateAchievements(evidence)` returns rule policy version 1, one check for each of the eight IDs, and a deduplicated `eligibleIds` list. It has no clock, IO, component state, save hooks or persisted unlock state. The caller supplies a canonical local `today` explicitly; an invalid date makes all checks unavailable. Inputs are not mutated, and repeated evaluation of the same evidence yields the same result.

Each check has a status and `confirmedProgress`:

| Status        | Meaning                                                                                                                                                        |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `eligible`    | Valid committed evidence proves this inclusive threshold, even if other history is missing. This does not mean the achievement has been persisted or unlocked. |
| `locked`      | Complete available evidence is below this threshold.                                                                                                           |
| `unavailable` | Evidence is missing, malformed, contradictory or insufficiently complete to decide a below-threshold result.                                                   |

`confirmedProgress` is a nonnegative confirmed lower bound capped at that rule's threshold. It is not an exact lifetime total. It is `null` for unavailable/invalid evidence, or a known partial value when an incomplete read still supplies valid evidence. Do not turn an unavailable result into zero, or use a later locked/unavailable evaluation to revoke a persisted unlock.

### Activity input

`AchievementActivityEvidence` contains `historyStartDate`, `pages` and `complete`. A null evidence object means a failed/unavailable read. `historyStartDate: null` with no pages represents no recorded history; `complete: false` keeps an uncertain empty result unavailable. With data, the start must be the earliest recorded date reported by the authoritative reader. Invalid metadata, a page before that start or pages accompanying a null start invalidate the activity stream.

Every page uses the existing `DailyStatisticsRange` contract, including its 366-day bound and full ordered per-date validation, and must have `bookId: null`. Multiple pages may span any recorded duration. Only dates through `today` contribute. If history is entirely future-labelled after clock rollback, confirmed activity through today is zero. The caller must mark unrecorded legacy history, missing pages or a partial read as incomplete. A completeness claim is additionally checked against unique coverage from `historyStartDate` through `today`; gaps and a missing final date prevent a known below-threshold result.

Native daily statistics already validate activity policy/origin, exclude import/restore credit and deduplicate operation/segment evidence. The evaluator does not accept editor submissions or raw manuscript counts. It deduplicates these global aggregates by local date, and goal results within a date are validated as unique by source book ID. Identical overlapping dates are accepted even if goal display order changes; conflicting repeats invalidate the whole activity stream instead of picking the larger count. Retained sources with null live book IDs still contribute.

Confirmed words, days and goals saturate at their largest rule thresholds before arithmetic can overflow. All pages are nevertheless validated, including those after a threshold is reached; later corruption cannot be hidden by an early success return. Malformed unsafe daily counters are rejected, while multiple individually safe days whose exact lifetime sum would overflow can still prove a small threshold safely.

### Completion input

Book evidence contains `snapshots` and `complete`, independently of the activity stream. It accepts the persistence-owned projection `id`, `createdAt`, `updatedAt`, `completedAt` from native book snapshots; full `Book` snapshots are structurally compatible. IDs must be canonical UUID-v4 values, timestamps canonical UTC milliseconds in years 0001–9999, and completion must fall between creation and update, matching native validation. No completion is inferred from a word target, activity result, title or current manuscript length.

Repeated identical book IDs are deduplicated; conflicting snapshots invalidate the completion stream. A valid non-null completion proves The End even in a partial collection. A complete empty collection or only null completions stays locked; a failed or incomplete negative read stays unavailable. Malformed completion evidence does not discard valid activity, and malformed activity does not discard valid explicit completion evidence. A later book deletion does not reconstruct missing completion evidence; retain durable unlocks in 6.3.

### Integration limit

The TypeScript evaluator remains pure domain logic; task 6.3 adds the native integration described below. Structural checks cannot establish transaction provenance for nonoverlapping pages or prove that arbitrary caller-created objects were committed. Independent calls to the existing per-range statistics API do not guarantee one snapshot. Native persistence therefore recomputes eligibility from SQLite instead of trusting caller-supplied eligibility IDs. ACH.1 remains the separate dependency for a user-facing explicit completion action.

## Permanent native unlocks (6.3)

Append-only migration `007_achievement_unlocks.sql` advances SQLite to **schema v7**. Earlier migrations are unchanged. The strict table has `achievement_id TEXT PRIMARY KEY`, `rule_policy_version INTEGER` and `unlocked_at TEXT`; ID/version constraints cover the eight policy-1 rules. There is no book foreign key, deletion cascade, manuscript snapshot or public unlock-removal command. Existing books, chapters, covers, goal history and activity are preserved.

`src-tauri/src/achievements/` owns native evidence collection, threshold evaluation, validated reads and inserts. It captures the native local date and reads all relevant evidence within one `IMMEDIATE` transaction, including uncommitted changes owned by the current chapter-save transaction. Only the outer commit makes that writing and its unlocks visible together. Clients cannot submit a date, totals, completion flags or eligibility IDs to the achievement IPC methods.

The native reader visits each distinct recorded activity date through today and calls the existing authoritative global daily-statistics reader for that date. Positive configured goals cannot be reached on dates without credited activity, so scanning empty calendar dates is unnecessary for these cumulative rules. This covers all history, including records over 366 days apart, and retains deleted sources. Imports/restores, zero-credit saves, scheduled state and sealed goals use existing validation/calculation policy. Saturating counters avoid unsafe lifetime sums, while every relevant row is still checked after thresholds are reached. Native-validated book snapshots provide explicit completion evidence. `tests/fixtures/achievement-rules.json` is checked by both Rust and TypeScript to prevent catalog/threshold drift.

Reconciliation validates existing unlock rows, then inserts eligible missing IDs using `ON CONFLICT(achievement_id) DO NOTHING`. Existing records are never updated. `unlockedAt` is a canonical native UTC instant from the initial successful insertion, with no inferred historical timestamp. Multiple eligible rules are inserted atomically. Two connections serialize through SQLite's writer lock; the primary key independently prevents duplicate identity. New rule policy versions must preserve this identity and require migration/compatibility review.

### Integration and errors

- **Startup:** after schema initialization and checks, reconcile historical committed evidence. Old manuscripts without credited activity earn no word achievements; historical eligible activity and explicit completion can be recognized once on upgrade. If reconciliation fails, startup reports the error without resetting or repairing the library. Schema migration and subsequent evidence reconciliation are separate transactions; an evidence failure may leave a successfully upgraded schema with all preexisting data intact.
- **Chapter saves and receipt retries:** reconcile after activity persistence and before the existing content-save commit, including successful frozen-payload retry recognition. Achievement insertion or final commit failure rolls back text, revisions, receipt, activity, day plans and new unlocks together. The existing editor save-error/draft retention flow remains responsible for retry; no success is returned before commit.
- **Book deletion:** after confirmation/revision/cover guards and before deletion, reconcile within that same transaction. This preserves a persisted explicit completion even if it has not yet been reconciled. Failed unlock insertion prevents deletion and retains the book. Later deletion or goal/schedule changes never remove an existing unlock. Chapter deletion already retains its activity.
- **Read/refresh failures:** malformed persisted evidence and SQL errors are explicit failures, never successful empty collections or guessed unlocks. Independent read/refresh failures do not remove existing unlocks. Native refresh fails as a whole on corrupt evidence; it does not partially persist the other stream. The pure 6.2 evaluator can describe partial evidence, while the native transaction requires authoritative successful reads.

### IPC and client boundary

`get_achievement_unlocks` is read-only and returns validated committed `{ achievementId, rulePolicyVersion, unlockedAt }` rows. `refresh_achievements` takes no client arguments, reconciles on the native local date and returns `{ unlocks, newlyUnlocked }` **after commit**. `newlyUnlocked` contains only rows inserted by that invocation; repeat refreshes return an empty new subset. Unlocks already inserted by startup or a save remain in `unlocks`, not in a later refresh's new subset. This result is not a notification delivery queue. Task 6.6 adds the separate receipt/claim contract described above.

`src/services/achievements.ts` exposes typed native-only access. Runtime guards reject unknown/duplicate IDs, unsupported policy versions, noncanonical timestamps and new rows absent from the committed result. Browser preview reports `desktop_required`; it has no persistence fallback. These services are available for the upcoming achievements UI but no page/cards/notifications are added in 6.3. A running app can request native reconciliation after a local-date change through `refresh_achievements`; startup and subsequent saves/deletions also reconcile. There is no achievement-specific background timer yet.
