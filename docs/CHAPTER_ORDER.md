# Chapter ordering (ED.19)

Writing Editor exposes a dotted drag handle on each chapter row. Drop a chapter on another row to move it to that row's position; dropping onto itself or outside the list does not write. The active target gets an outline. Up/down icon buttons provide keyboard and touch alternatives, with descriptive accessible names and disabled boundary actions. Successful moves focus the moved chapter heading and announce that the order was saved.

Reload chapters is now an icon button next to Create chapter. Its accessible name, tooltip, read behavior and pending/loading guards remain intact. Controls wrap on narrow/enlarged layouts.

ChapterManager sends the existing `reorder_chapters` command the full prior ID/revision vector and the desired ID permutation. A synchronous guard serializes moves; other chapter mutations and reload are disabled during the write. The displayed list stays in the last committed order until persistence succeeds. The committed response replaces positions/revisions, preserving chapter identity and existing manuscript/count metadata. Failure retains the previous list and shows an error. Revision conflicts ask the user to reload before trying again. No schema or native repository changes are needed; the existing transaction checks concurrent edits, membership and order.

The native window config sets `dragDropEnabled: false` to permit frontend HTML5 dragging on Windows. This setting and its WebView2 reason are documented in the [official Tauri configuration reference](https://v2.tauri.app/reference/config/#dragdropenabled) and the installed CLI schema. The app does not consume native file-drop events; cover file selection still uses its existing input. No dependency was added.
