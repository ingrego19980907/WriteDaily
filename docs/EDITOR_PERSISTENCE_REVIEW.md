# Desktop editor persistence and recovery (3.12)

Verified on Windows on 2026-10-26 with six real Tauri/WebView2 process launches and an isolated SQLite v4 library. This establishes **recovery of the last committed document**, not recovery of every keystroke: text still only in memory before autosave is lost on forced termination. That boundary was explicitly exercised. No durable draft journal or lossless power-failure guarantee is claimed.

## Reproduce and isolation

```powershell
$env:Path = "$env:USERPROFILE\.cargo\bin;" + $env:Path
npm.cmd run test:desktop:editor
```

This opens real application windows. tests/desktop/restart.ts reuses the existing native build/launch/window/close harness and selects tests/desktop/editor-restart.ts with --editor. The ordinary `npm.cmd run test:desktop` book/cover scenario remains available. No mock bridge, browser persistence or Vite server is used: CDP drives the embedded production UI and native read IPC checks committed snapshots.

Every run creates a fresh `.cache/desktop-restart/run-*` directory, private app-data and WebView2 profile, CLI-only appDirectoriesOverride config and copied write-daily-restart executable. Before any UI writes, the harness verifies that the private database exists with the expected application marker/schema. The production identifier/config file is unchanged. Real library directories are never selected.

All content/preferences writes use actual UI controls; direct native IPC is read-only. The only external database writes create/remove a fault-injection trigger in that newly created private database. The trigger stalls a content UPDATE with a constant-memory recursive SELECT, without large inserts. A separate connection with zero busy timeout proves that the application owns the SQLite writer lock. That probe connection closes before forcibly terminating the owned test process. No connection reopens the database until the next real app startup, so startup recovery is exercised by Tauri itself. The trigger is removed only after startup/document integrity is verified.

Forced termination is confined to the spawned child whose executable path exactly matches the copy in the fresh run directory. It never searches for or terminates arbitrary application processes. Failure cleanup can terminate only that same owned test child. Native screenshots use the existing PID-scoped helper; no real desktop/library data is deleted or reset. The default debug executable/config context is rebuilt in finally, and successful completion leaves no test application running.

## Verification and limits

Fresh checks: 401 Vitest tests, 66 Rust tests, lint, format:check, strict typecheck, Cargo fmt/Clippy and both isolated/default debug native builds passed. The 94 Edge tests remain the 3.11 result; production UI/native implementation/migrations/dependencies are unchanged in 3.12, so that suite was not repeated. The new command, common harness safety gate, editor scenario and documentation are the changes in this task.

Milestone 3 acceptance is satisfied for the implemented v1 editor and **commit-based recovery**. Normal close protects dirty/pending writing; abrupt termination preserves the last successful commit and later saves remain usable. **Unsaved in-memory changes do not survive a crash.** Assessment of a durable recovery journal is therefore complete: it is absent from this implementation and would be additional persistence/recovery design, not a capability supplied by this verification task. No automatic crash-draft restore or zero-loss claim is made.

This run does not simulate loss of power/storage hardware, every possible termination point, full disks, arbitrary corruption/migration histories, installer/macOS behavior or manual screen-reader use. Native failure/conflict/rollback tests and browser error/rapid-action checks retain their narrower recorded coverage. No production data or application code required repair. Book aggregation remains task 4.1.

ED.8 driver follow-up: font assertions now target persisted inline spans and explicit range/content saves; schema v4 and the legacy preference table remain. Additional formatting commits affect relative revision expectations. This updated driver has not been rerun; the actual launch evidence above describes the earlier global-preference implementation.
