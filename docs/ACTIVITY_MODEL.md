# Writing activity model (5.1)

Status: domain contracts and a pure delta policy are implemented in `src/features/activity/activity.ts`. Activity capture, SQL tables/migration, IPC, atomic save integration and queries are **not implemented**; they belong to 5.2 onward. Existing chapter saves are unchanged. This document is the implementation contract for that work.

## What counts

Policy version 1 uses the application's existing Unicode word-counting policy. For one contiguous edit batch, `addedWords = max(0, afterWords - beforeWords)`, `deletedWords = max(0, beforeWords - afterWords)`. `creditedWords` equals added words only for origin `editor`. Paste belongs to editor input and earns the same net credit as typing. Import and restore have zero credit; their content must never travel through a creditable editor submission as newly typed words. A whole-database restore preserves existing event IDs/history rather than replaying imported events.

Same-length replacement and formatting earn zero. Changes that cancel before a batch closes earn zero; this does not count keystrokes or diff individual inserted/deleted tokens. Deleting 20 saved words records 20 deleted words without removing historical credit. Retyping them in a later committed batch can earn 20 new words. Undo/redo follows the same rule. These are habit metrics, not fraud-resistant authorship measures. Chapter deletion is a lifecycle action, not a negative writing event.

Manuscript length, historical credited words and deleted words are separate quantities. Neither a book's existing length nor a newly calculated legacy count is historical activity. On an old chapter with `word_count = NULL`, native code must count the validated stored body as the before baseline and count the new body as the after endpoint; it must not use zero. Unknown/corrupt content blocks the write without inventing credit or resetting data. No migration backfills writing history from current manuscripts.

## Edit-time context and batches

An `ActivitySegment` has before/after word counts, first/last edit UTC timestamps and an `ActivityContext`: local `YYYY-MM-DD`, nullable IANA timezone name, UTC offset in minutes east of UTC, daily goal and scheduled-day snapshot. Counts are nonnegative safe integers. Goals are null or positive safe integers. Dates use shared canonical calendar validation; instants use the existing canonical UTC-millisecond convention. Offsets are integers from -840 through +840; timezone names are bounded nonempty strings when supplied, with offset-only fallback when unavailable. The offset sign is the negative of JavaScript `getTimezoneOffset()`.

Capture context when text transactions happen, not when a debounce fires. A segment continues while local date, timezone name, offset, goal and schedule context match. Close it on any context change and begin the next segment with the previous after count. Check current local context on every edit; do not rely on midnight timers firing while the app is suspended. DST offset changes split segments even on the same date. Midnight without an edit creates no synthetic writing event. Record the date/offset observed at edit time; stored dates are never moved when the user later changes timezone.

Example: stored 100 words; an edit at 23:59 reaches 120; an edit at 00:01 reduces it to 110; one eventual save persists both segments. The earlier date receives 20 credited words, the later date receives 10 deleted words and zero credit. Assigning a net 10 words to the save date would be wrong. A save with several segments is atomic across all of them. Positive/negative/positive changes within one unchanged context use the net endpoints of that batch; context boundaries intentionally affect batch attribution.

Wall clocks may move backward. Preserve segment sequence rather than sorting by timestamps; do not require lastEditedAt to be later than firstEditedAt or infer elapsed session duration. Consecutive appearances of the same local date aggregate to that calendar label, even after travelling across timezones. No timed writing-session duration or idle-time measurement is fabricated from save timestamps.

## Submission, authority and retries

`ActivitySubmission` contains policyVersion 1, a UUID-v4 operationId, origin and ordered segments. It is attached to a single content-save request with the existing source book/chapter IDs, expected chapter revision and submitted content. Native code remains authoritative for source ownership, persisted before count, submitted after count, supported policy/origin, field limits, goal/schedule validity and segment-chain continuity. Segment zero starts at the native stored-body count; each next before count equals the prior after count; the final after count equals the native submitted-body count. Intermediate edit-time segments are observations from the local editor, not a cryptographic proof of keystrokes. Existing metadata/reorder/create/delete operations do not manufacture activity. A formatting-only body commit can carry a zero-delta editor segment; daily activity/active-day counts require positive credit.

Allocate operationId once when freezing the save payload. Retry the same operation with exactly the same content/context/segments; do not reuse it for another payload or regenerate it after an uncertain commit. Store a native receipt keyed by operationId, immutable source IDs, expected and committed revision, policy/origin and a SHA-256 digest of the canonical semantic save payload. Canonical digest input must include content, source IDs, expected revision and all ordered segment fields. Canonicalization and digest implementation/compatibility must be verified in 5.2; no crypto dependency is installed in 5.1.

Within one IMMEDIATE transaction, check an existing receipt before rejecting a stale chapter revision. The same operation ID and matching digest means already committed: return a receipt acknowledgment without adding credit, rewriting content or returning stale content as current. If the chapter has since advanced, return its separately validated current snapshot/explicit advanced outcome; never overwrite newer writing with the old receipt snapshot. A reused ID with different payload is a visible conflict. A receipt for a deleted source can acknowledge a prior commit but cannot recreate the chapter. A new ID with a stale revision remains a normal conflict, not a duplicate acknowledgment.

If there is no receipt, validate the current revision and full payload, persist content/count/revision, receipt, segments and applicable day plans, then commit. Only afterward report saved. Any validation/SQL/commit failure leaves all of these unchanged. If a write fails before commit, retain the original frozen payload for explicit retry; further edits must not be appended to that same operation. Failed/conflicting writes and discarded unsaved drafts earn no activity. Session-memory segments share the existing editor's crash limit: only committed activity survives termination; no durable unsaved activity journal is claimed.

## Planned persistence and retention

These are constraints for an append-only migration in 5.2, not tables already present in schema v4:

| Table               | Identity and fields                                                                                                                                                                                                                    | Constraints/lifecycle                                                                                                                                                                                             |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| activity_operations | operation_id, policy_version, origin, immutable source_book_id/source_chapter_id, expected_revision, committed_revision, payload_digest, committed_at                                                                                  | Unique UUID operation ID, supported versions/origins, safe positive revisions, digest of frozen canonical request; receipt retained even for zero-credit saves or deleted sources                                 |
| writing_activity    | operation_id + segment_index, nullable live book_id/chapter_id, immutable source IDs via operation, local_date, timezone, offset, first/last edit instants, before/after counts, added/deleted/credited words, goal/scheduled snapshot | Composite unique event identity; segment indexes contiguous and bounded per operation; immutable event facts; counts/checks validated natively; live foreign keys use ON DELETE SET NULL, not CASCADE             |
| activity_day_plans  | immutable source_book_id + local_date, nullable live book_id, daily_word_goal, scheduled, policy_version                                                                                                                               | First committed editor segment for the book/date seals that day's goal/schedule, including zero-delta segments; later segments use the existing plan for results. Import/restore cannot create a writing-day plan |

Store only metadata/counts/context, not a duplicate manuscript, title, clipboard text or per-keystroke log. Native input decoding rejects unknown fields/unsupported versions, unsafe values and oversized requests before persistence. Set explicit segment/payload limits in 5.2 and fail visibly without truncating or coalescing different contexts. If a cap is approaching during editing, flush safely before admitting more segments; never discard unsaved writing to fit telemetry.

Retain operation receipts, events and sealed day plans indefinitely, without background pruning. Deleting a chapter detaches chapter_id while preserving its book link until the book is deleted; deleting a book detaches both live links through the existing chapter cascade and SET NULL event references. Immutable source UUIDs keep events attributable and receipts verifiable without retaining deleted writing/titles. Global historical totals/streak/achievement evidence survive; normal current-book queries exclude detached/deleted books. Include these tables in future backups. Restore must preserve unique IDs and never credit restored rows again. There is no separate activity-history deletion UI in this scope.

For day-level goal results, the sealed plan wins over later configuration edits. Changing a book goal after its first committed editor segment affects future unsealed dates, not already sealed history; the UI must distinguish configured goals from an applicable sealed day goal. A null goal is unconfigured, not a zero-word achievement. All days are scheduled until 5.7 implements preferred days and effective-dated history. Dates without an event/plan cannot be assigned historical goal/schedule results from today's configuration; 5.7 must supply effective history for empty dates. Goal/streak aggregation, scheduled-day grace and multi-book presentation remain 5.3–5.8, not inferred here.

Types are design contracts, not runtime validation of arbitrary activity payloads. Tests do not claim receipts, deduplication, transaction atomicity, timezone capture or deletion retention are already implemented.
